# LightCraft Cloud — десктопний інтерфейс

Розділ Cloud інтегровано в наявний egui-застосунок LightCraft. Він працює з незалежним
Rust Backend з етапу 3. Перевірки виконуються лише в Codex; підключення до OCI, зміни
Immich, Nginx Proxy Manager чи розгортання на сервері користувача не виконуються.

## Як користуватися

1. Відкрийте **Cloud Library** на бічній панелі або натисніть значок хмари вгорі.
2. У **Settings → Cloud** введіть кореневу HTTPS-адресу власного API, наприклад
   `https://cloud.example.com`. Для локальної розробки дозволено HTTP на loopback.
3. Натисніть **Save & test connection**. Перевіряються готовність API, його публічна
   конфігурація та OIDC discovery. Адреса зберігається в наявних налаштуваннях LightCraft.
4. Натисніть **Sign in with browser**. LightCraft відкриває Keycloak у системному браузері;
   пароль вводиться там. Після входу поверніться до LightCraft.
5. Створіть бібліотеку, виберіть **Upload RAW / JPEG** або перетягніть файли у вікно Cloud.
   Прогрес показує обчислення хешу та передавання поточного файлу. До 128 файлів у пакеті;
   максимальний розмір одного оригіналу визначає сервер (клієнт підтримує до 512 MiB).
6. Виберіть фото й натисніть **Download original**. Наявні локальні файли не перезаписуються.
   До завершення перевірки розміру та SHA-256 завантаження залишається тимчасовим файлом.
7. **Load image** завантажує оригінал у тимчасовий каталог, перевіряє його й будує мініатюру.
   Для RAW потрібен підтримуваний вбудований JPEG; розмір для цього перегляду обмежено
   128 MiB. Тимчасовий оригінал видаляється, у пам'яті зберігається до 48 мініатюр.
8. **Local Library** повертає до локального каталогу та редактора. Завантажений оригінал
   можна імпортувати звичайними засобами LightCraft. Хмарні правки поки не синхронізуються.

Сітка показує реальні серверні записи, назву, формат, розмір і стан зберігання. Є пошук
за назвою серед завантажених записів, вибір бібліотеки, оновлення та пагінація по 100 фото.
На вузьких вікнах бібліотеки згортаються, а кнопки оригіналу переміщуються над сіткою.
Помилки адреси, мережі, доступу, сховища й цілісності мають окремі повідомлення.

## Авторизація та секрети

Використовується наявний публічний клієнт Keycloak `lightcraft-desktop`, Authorization Code
із PKCE S256, випадковими state/nonce/verifier та перевіркою RS256 ID token. Loopback
callback `http://127.0.0.1:47861/callback` слухає лише під час входу; зайнятий порт дає
зрозумілу помилку. HTTPS discovery/token/JWKS endpoints перевіряються на відповідність
issuer; HTTP redirects для API та токенів вимкнено.

Access token живе тільки в пам'яті. За ввімкненого **Remember sign-in** refresh token
зберігається в macOS Keychain, Windows Credential Manager або Linux Secret Service.
Налаштування містять тільки адресу сервера та прапорець запам'ятовування. Якщо системне
сховище недоступне, UI повідомляє про вхід тільки на поточний сеанс; plaintext fallback немає.
На Linux потрібен розблокований Secret Service у користувацькій D-Bus сесії.

**Sign out** видаляє локальний refresh token і запитує завершення сесії Keycloak. Якщо
мережа недоступна, локальний вихід завершується з повідомленням про невдале відкликання.
Якщо відомий збережений токен не можна видалити зі сховища, успішний вихід не заявляється.
Коли сховище було недоступне вже при вході, вихід очищає сеанс у пам'яті, але повідомляє,
що видалення можливих попередніх збережених облікових даних не вдалося підтвердити.
При зміні сервера попередній вхід прив'язаний до попередньої адреси; для його видалення
спочатку виконайте вихід із того сервера. Приватні ключі, паролі й токени не потрібні в Git.

## Реальні API, використані інтерфейсом

| Метод | Endpoint | Призначення |
|---|---|---|
| GET | `/health/ready` | Перевірка готовності |
| GET | `/v1/config` | Новий мінімальний публічний endpoint: api_version, issuer, client_id, max_upload_bytes |
| GET | `/v1/me` | Ідентичність користувача після входу |
| GET / POST | `/v1/libraries` | Список / створення бібліотеки |
| GET / POST | `/v1/libraries/{id}/photos` | Список / реєстрація оригіналу з operation_id |
| GET | `/v1/photos/{id}` | Перевірка результату після втраченої відповіді на upload |
| PUT / GET | `/v1/photos/{id}/original` | Передавання / отримання незмінених байтів |
| DELETE | `/v1/photos/{id}/upload` | Скасування незавершеного upload intent |

OIDC discovery, authorization, token, certs і logout використовують наявний realm Keycloak.
Міграції та модель зберігання етапу 3 не змінювалися. `/v1/config` має бути доступний
у версії API, до якої підключається UI. Сервер перевіряє права власника для кожного ресурсу.

## Межі цього етапу

Реалізовані ручні одноразові передачі з повтором після помилки. Retry використовує той
самий operation ID у поточному сеансі; скасована передача запускається знову як нова.
Скасування кооперативне: під час завислого мережевого читання можливе очікування timeout
(до 330 секунд для оригіналу). Закриття програми під час операції потребує явного вибору.

Альбоми, серверні прев'ю, постійний офлайн-кеш, автоматична двостороння синхронізація,
правки, рейтинги, теги та відновлення передач із байтової позиції ще не реалізовані.
UI прямо повідомляє про відсутність альбомів і серверних прев'ю. Метадані, які вже надає
сервер, відображаються як властивості оригіналу; витягування EXIF при upload буде окремою
роботою. Для етапу 4 залишаються upload sessions/chunks, черга з відновленням після
перезапуску, серверний preview worker/API та обмежений постійний кеш.

## Відтворення перевірок

Звичайні перевірки без зовнішнього сервера:

```sh
cargo test -p lightcraft-cloud-client
cargo test -p lightcraft-ui-egui cloud::tests:: -- --test-threads=1
cargo xtask ci --summary-md
cargo build -p lightcraft
```

Інтеграційний UI-тест без змін реального сервера потребує окремого локального Compose
стека з `cloud/README.md` та розблокованого **тестового**, ізольованого OS credential store.
У Codex Linux використовується окрема D-Bus сесія й тимчасовий профіль gnome-keyring.
Не запускайте тест із власним обліковим записом чи production Keycloak.

```sh
export LC_TEST_API_URL=http://127.0.0.1:18880
export LC_TEST_AUTH_URL=http://127.0.0.1:18881
python3 cloud/tests/desktop_browser.py prepare
export LC_CLOUD_UI_TEST_SERVER="$LC_TEST_API_URL"
export LC_CLOUD_UI_BROWSER_HELPER="$PWD/cloud/tests/desktop_browser.py"
export LC_CLOUD_UI_TEST_OUTPUT=/tmp/lightcraft-cloud-ui-evidence
cargo test -p lightcraft-ui-egui --lib \
  cloud::tests::cloud_real_backend_browser_upload_download_restart_and_logout \
  -- --exact --nocapture --test-threads=1
```

`prepare` створює випадковий тестовий обліковий запис через bootstrap локального стека;
його секрети залишаються в ігнорованому `.secrets/desktop-e2e.json` із правами 0600.
Драйвер проходить справжню HTML-форму Keycloak і callback PKCE; він не підставляє токени
в застосунок. UI працює через наявний Headless renderer та реальні команди/кнопки.
Скріншоти є результатом рендерингу LightCraft. Фотографії для тесту процедурно генеруються
з власних demo-сцен; DNG є синтетичним контейнером для перевірки байтового передавання,
а не доказом декодування сенсора конкретної камери. Тест запускає другий процес для
перевірки відновлення входу та виходу через системне сховище.

## Перевірено в Codex

- Повний `cargo xtask ci --summary-md` пройшов усі 8 етапів: fmt, clippy,
  heif, test, parity, layers, assets та wasm. У виконаних перевірках регресій
  редактора не виявлено. Звіт CI реєструє 192 умовні пропуски: corpus 137,
  GPU 25, fonts 20, model 8, system 2. Бракує набору камерних RAW, GPU,
  додаткових шрифтів, моделей та системних ICC-профілів; це обмежує покриття.
  Один із system-пропусків — Cloud E2E, який окремо виконано успішно нижче.
- Усі 7 тестів `lightcraft-cloud-client` пройшли: адреси, callback state/issuer,
  цілісність і неперезапис оригіналу, відмова від redirects, 401, збереження сеансу
  при перевірці сервера, недоступний credential store і допустимі RAW/JPEG розширення.
- Реальний UI-сценарій через локальні Keycloak, PostgreSQL і файлове сховище: вхід PKCE,
  перевірка сервера без втрати входу, створення бібліотеки, upload чотирьох JPEG і
  синтетичного DNG, п'ять серверних записів і мініатюри, побайтовий download DNG,
  захист наявного локального файлу, відновлення через Secret Service в новому процесі,
  logout і відсутність автоматичного входу після нього, помилка недоступної мережі — пройшов.
- Окремі UI-регресії перевіряють вузьке/широке вікно, збереження публічних налаштувань,
  незмінність локальних правок у Cloud, некоректні адреси та підтвердження закриття
  під час активної операції. Без налаштованого локального стека реальний E2E явно
  реєструє skip; наведений вище запуск виконував його окремо.
- Backend: Clippy з `-D warnings`, 14 модульних/інтеграційних Rust-тестів та всі 8
  Python E2E-тестів пройшли, включно з перестворенням контейнерів і перевіркою даних.
- API з `/v1/config` зібрано як статичний `aarch64-unknown-linux-musl` бінарний файл
  і Docker-образ `linux/arm64`. Локальні E2E виконано з ARM64 API під QEMU;
  PostgreSQL і Keycloak працювали на amd64. Це не тест на реальній Oracle VM.
- Скриншоти отримано з Headless renderer наявного LightCraft; переглянуто сітку,
  Settings і компактне вікно. Native GUI/compositor та сховища Windows/macOS
  у цьому Linux-середовищі не перевірялися.
- `cargo build -p lightcraft` успішно створив Linux x86_64 desktop executable;
  запуск `target/debug/lightcraft --version` повернув `lightcraft 0.9.1`.
